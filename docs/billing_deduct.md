# 自动扣费模块开发需求（数据源：pod_info_history_v2）

> 状态：需求讨论稿 v0.1
> 关联模块：billing（bill / wallet / price_config / account_log / bill_item）

## 一、背景与目标

平台已上线计费模块（费用明细 bill、钱包 wallet、单价配置 price_config、资金流水 account_log）。费用来源目前是**外部清单推送 + 手动扣费**。

公司内网有一套扫描脚本，每 5 分钟扫描平台在线任务，把每个任务（pod）的资源占用**按天**写入 `pod_info_history_v2`（同一天同一 `pod_uid` 只记一条，`duration` 为该 pod 从创建到当次的**累计运行小时数**）。

**本模块目标**：平台依据 `pod_info_history_v2` 快照自动计算任务费用 → 生成扣费单 → 推送给用户确认（同意/质疑）→ 同意后扣钱包入账。管理员可手动执行或按周期定时执行。

## 二、计费口径（核心规则）

| 项 | 规则 | 说明 |
|---|---|---|
| 任务标识 | `pod_uid` | 改规格 = 重启任务 = 新 pod_uid，不存在中途规格变化问题 |
| 有效任务 | `status='Running'` **且** `duration > 最低付费时长阈值` | 阈值管理员可配置（默认 10 分钟） |
| 计费时长 | `最新快照 duration − 上次已扣 duration` = 本次增量；首扣 = 全部时长 | **增量结算**：任务续跑、多次扣费不重复收；已结束任务 duration 定格，自动不再扣 |
| 资源规格 | 最新快照的 `gpu_usage` / `mem_limit_gb` / `cpu_limit` | GPU 卡数 = `gpu_usage / 100`（100=整卡，50=半卡） |
| GPU 型号 | 快照 `node_name` JOIN `all_node_memory.node_name` 取 `gpu_type` | `gpu_type=NULL` = CPU 节点，不收 GPU 费；**node_name 查不到时按 L20 兜底**（已确认） |
| GPU 单价 | 按型号从 price_config 读取（A40/L20/A100/H100...） | 例：L20 = 2000 元/卡/月 |
| CPU / 内存单价 | 复用 price_config：CPU 200 元/核/月、内存 100 元/GB/月 | |
| 月价→小时价 | 单价月价 ÷ 720（30 天） | 折算系数可配置 |
| 用户归属 | 快照 `username` ↔ `ab_user.username` | **对不上的跳过不扣费 + 记日志**（已确认） |
| 白名单 | 按 **部门(org) / 用户 / 集群** 维度（已确认） | 白名单内任务不收费 |
| 钱包余额 | **允许负余额**（先扣后补，不拦截）（已确认） | |
| 金额 | 统一整数"分"结算 | 避免浮点误差 |

## 三、扣费单状态机

```
draft(已计算,待推送) ──推送──> pushed(已推送给用户)
                                  ├── 用户同意 ──> agreed(已同意) ──入账扣款──> settled(已扣款)
                                  ├── 超时未处理(默认7天,管理员可配) ──> agreed(自动同意) ──> settled
                                  └── 用户质疑 ──> disputed(有异议)
                                        │  管理员处理：
                                        ├── 改价重推 ──> draft/pushed（用户重新确认）
                                        ├── 驳回质疑 ──> agreed（按原金额继续）
                                        └── 作废 ──> cancelled（本次不扣）
```

- 入账动作（钱包扣款 + account_log 流水）只在 **settled** 时执行一次，幂等
- 每张扣费单关联一个"扣费批次"（billing_run），一次执行生成一个批次
- **超时自动同意**：pushed 状态超过 N 天（管理员可配置，默认 7 天）未处理 → 自动转 agreed 并扣款；推送时告知用户"X 天内未处理将自动扣费"

## 四、功能清单

### 1. 管理员端

**1.1 扣费规则配置页**
- 最低付费时长阈值（分钟，默认 10）
- 月价→小时价折算系数（默认 720）
- 超时自动扣费天数（默认 7 天，可自定义）
- GPU 型号来源：`node_name` JOIN `all_node_memory`（查不到按 L20 兜底）
- 计费项开关（cpu / memory / gpu 是否参与计费）
- 功能总开关（关闭后定时任务不执行）

**1.2 白名单管理页**
- 按 **部门(org) / 用户 / 集群** 三个维度添加白名单，支持启用/停用/删除
- 执行扣费时命中任一维度白名单的任务跳过，并计入"跳过原因"统计（可查命中的是哪个维度）

**1.3 手动执行扣费**
- 按钮"立即执行一轮扣费"：跑完整计算流程，生成一批 draft 扣费单
- 展示本轮结果：生成 N 单 / 跳过 M（白名单、未达阈值、增量=0、用户不匹配）

**1.4 定时扣费设置**
- 管理员设置执行周期（每日 / 每周 / 每 N 天 / 指定时刻），可启用/停用
- 定时执行与手动执行共用同一套计算逻辑

**1.5 扣费单管理页**
- 列表：按批次 / 状态 / 用户 / 时间筛选
- 详情：任务信息（pod_name、namespace、创建时间）、资源规格、计费时长区间、单价、金额、质疑记录
- 操作：批量推送、处理质疑（改价/驳回/作废）、查看资金流水

**1.6 扣费批次页**
- 每次执行一条记录：执行方式（手动/定时）、执行人、执行时间、生成/跳过统计

### 2. 用户端（我的账单）

**2.1 我的扣费单列表**：本人所有扣费单（复用/扩展 my.html），展示状态、金额、任务、周期
**2.2 扣费单详情**：资源规格（GPU 卡数/显存、内存、CPU）、计费时长、单价、金额明细
**2.3 同意 / 质疑**：质疑需填写理由；同意后进入扣款流程；推送时会提示"X 天内未处理将自动扣费"，超时未处理自动同意并入账
**2.4 扣款结果**：钱包余额变动 + account_log 流水可见（已有）

**2.5 我的历史 Pod 记录**（新增）
- 入口：我的账单页新增 Tab / 按钮"我的Pod记录"
- **两级展示**：
  - 任务列表：按 `pod_uid` 聚合**最新快照**（pod_name、状态、显卡型号(JOIN all_node_memory)、资源规格、累计时长、最后更新时间）
  - 快照明细：点击任务查看**按天快照**（每天一条的 gpu/mem/cpu/duration 变化轨迹，可对照扣费单的计费区间）
- 筛选：状态、时间范围、pod_name 模糊搜索
- **只展示当前登录用户自己的记录**（快照 `username` = 登录用户名，行级隔离）
- **任意组合筛选**（已确认）：状态、时间范围、pod_name 模糊、pod_uid、命名空间、集群、节点、GPU 型号，自由组合 + 排序 + 大数据量分页（索引 + 分批加载）
- 也是用户质疑扣费单时的核对依据

### 3. 推送机制（站内通知，已确认）
- 用户登录后在我的账单页看到待确认扣费单（未读标记）
- **既支持一键全推，也支持单张/多选推送**（已确认）
- 推送时展示自动扣费时限提示（"X 天内未处理将自动扣费"）
- 后续可扩展：邮件 / 企微 Webhook

## 五、数据模型变更

### 现有表调整
- **bill**：去掉 `pod_name` 唯一约束（一个 pod 允许多次扣费记录），新增：
  - `pod_uid`（任务标识，索引）
  - `billing_run_id`（批次外键）
  - `deduct_from_hours` / `deduct_to_hours`（本次计费时长区间，便于核对）
  - 状态扩展：`draft / pushed / agreed / disputed / settled / cancelled`（现有 settled/failed 兼容迁移）
  - `source='history'`（区分外部推送/手动扣费）
- 外部推送接口幂等改为应用层判断（pod_name + source 查重），行为不变

### 新表
- **billing_run**：批次（id、执行方式 manual/scheduled、执行人、执行时间、生成/跳过统计、说明）
- **bill_dispute**：质疑（bill_id、质疑用户、理由、处理人、处理意见、处理结果、时间）
- **bill_whitelist**：白名单（维度 user/org/namespace、值、备注、创建人、启用）
- **billing_config**：规则配置（key-value：min_duration_minutes、month_hours、enabled 等）

### 外部只读表
- **all_node_memory**：节点 → 显卡型号映射（`node_name` 唯一、`gpu_type` NULL=CPU 节点）。本地已建简化结构并灌入假数据；生产以 AI 库实际表结构为准，只依赖 `node_name` + `gpu_type` 两列做 JOIN

### 索引
- `pod_info_history_v2 (pod_uid, update_at)` —— 按任务取最新快照
- `pod_info_history_v2 (username, update_at)` —— "我的Pod记录"查询（行级隔离）
- `all_node_memory (node_name)` —— 关联查询（本地已建唯一索引）
- `bill (pod_uid)`、`bill (billing_run_id)`、`bill (status)`

## 六、定时执行方案

- 复用项目已有 celery 基础设施：启用 beat + worker 服务（compose 中已有注释配置，放开即可）
- 定时任务：读取 billing_config 周期 → 自动执行一轮扣费
- 失败重试与日志（celery 自带）；执行结果落 billing_run

## 七、健壮性与数据质量

1. **duration 是 varchar**：解析容错（空值/非数字/负数 → 跳过并记录）
2. **快照缺失某天**：增量口径只依赖"最新快照 − 上次已扣"，天然免疫 ✅
3. **并发防重**：手动与定时同时触发时，同一批次锁/任务锁保证同一 pod 不重复扣费（同 pod 增量=0 自然跳过 + 批次唯一约束双保险）
4. **金额精度**：全程整数分；卡数×小时×单价 换算后四舍五入
5. **性能**：62 万行数据按索引分批处理（游标分页），不一次性加载
6. **幂等**：同一批次重复执行不产生新账单（批次号唯一；已扣时长不变则增量=0）
7. **用户不匹配**：跳过并汇总展示（管理员可在批次详情看到）

## 十、验收效果（达到的样子）

1. 管理员点"执行扣费" → 一轮计算完成，生成批量扣费单（只收 Running 且超阈值、跳过白名单、跳过对不上账号的 pod）
2. 管理员批量推送 → 用户在"我的账单"看到待确认扣费单
3. 用户点同意 → 钱包扣款 → 资金流水/账单明细可见
4. 用户点质疑（填理由）→ 管理员在扣费单管理看到异议 → 改价重推 / 驳回 / 作废
5. 任务续跑一个月后再次扣费 → 只扣新增时长，不重复收
6. 管理员配置周期后 → 定时任务自动执行，批次记录可查

## 十一、我补充的考虑点（你没想到的）

1. **并发防重**：手动+定时同开，需要批次锁
2. **钱包余额不足**：现有 Wallet 允许负余额——建议允许为负（先扣后补），不做拦截；若需拦截再讨论
3. **退款/冲正**：扣错费时复用 account_log 的 reversed 冲正机制，管理员可冲正
4. **白名单变更的时机**：白名单在执行扣费时读取生效；已生成的 draft 单在推送前管理员可重算/作废
5. **已推送但用户长期不处理**：建议"推送后超 N 天未回应自动视为同意"（可配置，默认不做，先人工催收）
6. **通知渠道**：第一版站内，预留邮件/企微扩展位
7. **时区**：定时任务按 Asia/Shanghai
8. **灰度开关**：billing_config.enabled 总开关，关闭时定时不跑、页面提示
9. **金额核对口径展示**：扣费单详情必须展示"本次时长区间（上次扣到 X → 本次扣到 Y）"，这是用户质疑时最常对的口径
10. **已结束任务的处理**：任务结束后最新快照不再更新，若结束前未扣过费，最后一次执行会按全部时长扣掉（合理）；若已扣过，增量=0 自动跳过（合理）——无需特判
11. **数据量增长**：bill 表将随扣费次数增长（一个 pod 多条），需定期归档策略（可选，后期）
12. **测试环境**：本地 3 条样例数据可验证全流程（两用户、一任务两条快照、不同规格）
